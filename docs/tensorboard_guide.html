Launching TensorBoard

Training (MaskablePPO from sb3-contrib) writes event files to tensorboard_logs/, one subfolder per run. Point TensorBoard at the parent folder to compare runs side by side.

tensorboard --logdir tensorboard_logs/ # then open http://localhost:6006

Scalars are grouped by a prefix/: rollout/ = what happened in the games, train/ = what the optimizer did, time/ = throughput. The X axis is total_timesteps (environment steps seen so far).

rollout/  Game-outcome metrics

These are the metrics that tell you whether the agent is actually getting better at Duck Chess. Watch these first.

rollout/ep_rew_meanmost important

Mean reward per finished episode, averaged over a rolling window (100 episodes). This is the single best "is it learning?" signal — it should trend up.

Values depend on the reward scheme. Sparse terminal reward (league / v2 / antiexploit stages): roughly −1 → +1, where +1 = win by king-capture, −1 = loss, 0 = the 50-move draw. Dense-shaped reward (older train_real/train_strong runs): unbounded, can read in the tens — only the trend is comparable, not the absolute number across schemes.

rollout/ep_len_mean

Mean number of steps (half-moves) per episode. In Duck Chess each turn is two phases, so length tracks how long games last before a king capture, fowling, or the 100-half-move draw cap.

Typical: tens up to ~100+. A collapse toward very short episodes early = the agent is hanging its king fast; a flat line pinned near the draw cap = games stalling out. Rising then stabilising is normal as play gets more competent.

rollout/ep_rew_mean vs. eval scoresnote

Self-play reward reflects performance against the training opponents, not a fixed benchmark. Treat rising ep_rew_mean as a training signal and confirm strength separately with eval_vs_peter.

train/  Optimizer / loss metrics

These are the standard PPO diagnostics. You don't optimise them directly — you read them to check the update is stable and neither exploding nor stalling.

train/entropy_loss

Negative mean policy entropy. Entropy = how random/exploratory the policy is. It starts high (very negative loss, near −ln(#legal actions)) and should drift toward 0 as the policy commits to good moves.

healthy a slow rise toward 0.   bad collapses to ~0 almost immediately = premature convergence / no exploration.

train/policy_gradient_loss

The clipped PPO surrogate (policy) loss. It's a surrogate objective, so its sign/magnitude is not "goodness" — watch that it stays small and doesn't diverge.

Typically small, hovering near 0 (e.g. −0.05 … +0.02). Wild swings signal instability.

train/value_loss

MSE of the value head predicting the return. In ExIt this is the head that matters for MCTS. Should decrease and level off.

Scale follows the reward scale. For sparse ±1 reward, expect it to settle < ~0.25. Rising steadily = value head can't fit the returns (too-high LR, or targets too noisy).

train/explained_variancekey health

How much of the return variance the value head explains. 1.0 = perfect, 0 = no better than predicting the mean, negative = worse than the mean (broken).

good > 0.5   ok 0–0.5   bad < 0. Early training near 0 is normal; it should climb.

train/approx_kl

Approx. KL divergence between the policy before and after each update — how far each step moves the policy.

Target band roughly 0.003 – 0.03. If it spikes > ~0.05 the updates are too aggressive (lower LR or clip range). Near 0 = barely learning.

train/clip_fraction

Fraction of samples where the PPO ratio hit the clip boundary. Indicates how often the policy wanted to move further than clip_range allows.

Healthy typically 0.05 – 0.2. Persistently high (> ~0.3) = updates too large.

train/clip_range  ·  train/learning_rate

The current PPO clip range and LR. Flat unless you use a schedule; plotted so you can see decay if one is set.

Common defaults: clip_range 0.2, learning_rate ~3e-4 (may decay toward 0).

train/loss  ·  train/n_updates  ·  train/std

loss = total combined loss (policy + value·vf_coef + entropy·ent_coef). n_updates = cumulative gradient updates (a monotonic counter). std appears for continuous actions only — not expected here since Duck Chess uses a discrete 4096 action space.

time/  Throughput metrics

Not about learning — about how fast the run is going. Useful for estimating when a build finishes.
